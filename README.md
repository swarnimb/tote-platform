# Tote Platform

Two operations tools for an IBC tote business, shown side by side as v1 and v2.

**Live demo → https://swarnimb.github.io/tote-platform/**

| | v1 — Tote-Ops | v2 — ToteTrack |
|---|---|---|
| **Side of the business** | Buy side: suppliers, pickups, gradeouts, invoicing | Sell side: customers, purchase orders, production, leads, invoicing |
| **Stack** | FastAPI · Jinja templates · SQLAlchemy · Alembic · PostgreSQL · CDN JS | Next.js 14 App Router · React Server Components · Server Actions · Drizzle · Supabase · Tailwind · shadcn/ui · Framer Motion · Recharts |
| **Frontend approach** | Server-rendered HTML, inline styles, no build step | Typed component library, design tokens, motion, charts |
| **In this repo** | Runs locally · screenshots in `assets/v1-tote-ops/` | Deployed to GitHub Pages · screenshots in `assets/v2-totetrack/` |

---

## What this repo is

A **demo and portfolio repo**. It is not production, it is not deployed for anyone's daily use, and it is not where either application is developed.

Both applications are real and both are in daily use by their owners. This repo carries a copy of each codebase and a fully synthetic dataset, so the two can be run, screenshotted and compared without touching anything real.

**All data in the demo is invented.** Every company, contact, address, phone number, email, order and dollar figure is generated by the seed scripts in this repo. No real supplier, customer or person appears anywhere.

## Running v1 — Tote-Ops

Needs Python 3.11+ and a local PostgreSQL.

```bash
cd v1-tote-ops
python -m venv .venv && .venv/Scripts/activate      # source .venv/bin/activate on macOS/Linux
pip install -r requirements.txt
cp .env.example .env                                 # point DATABASE_URL at a local database
alembic upgrade head
python seed_demo.py
python -m uvicorn app.main:app --port 8011
```

The login password is whatever you set as `APP_PASSWORD`. The Supabase values in `.env` can stay as placeholders — that client is only reached by gradeout PDF upload, which the demo does not use.

To recapture the screenshots (needs `pip install playwright && playwright install chromium`):

```bash
python screenshot_demo.py
```

## Running v2 — ToteTrack

Needs Node 20+ and a local PostgreSQL.

```bash
cd v2-totetrack
npm install
cp .env.example .env.local                           # point DATABASE_URL at a local database
node db/demo/setup-db.mjs                            # applies the schema
npx tsx --env-file=.env.local db/seed-demo.ts        # seeds synthetic data
npm run dev
```

To build the static demo exactly as GitHub Pages serves it:

```bash
NEXT_PUBLIC_DEMO_MODE=true npx next build
node scripts/write-root-redirect.mjs
npx serve out                                        # or any static server
```

## Rebuilding the before/after pairs

```bash
cd tools
npm install && npx playwright install chromium
npm run build:before-after
```

## How the static demo works

GitHub Pages serves static files only, and ToteTrack is Server Components and Server Actions end to end. Rather than rewrite the data layer against fixtures, the demo **prerenders the real application against a locally seeded PostgreSQL at build time** — so the published HTML carries genuine query output, with no database or Supabase project behind it at runtime.

Everything that makes that possible is gated on `NEXT_PUBLIC_DEMO_MODE`, which is never set in the production repo. With it unset, `next.config.js` is byte-identical to the original and both route segment configs still evaluate to `force-dynamic`.

With it set:

- `output: 'export'`, `basePath: /tote-platform`, unoptimized images
- every `'use server'` module the UI imports is swapped by a webpack module replacement for a read-only shim in `lib/demo/actions/`, which returns the same `{ error }` shape the real actions use for failures — so the existing toasts surface "read-only demo" with no component changes
- the cookie-reading Supabase server client is swapped for a stub, because prerendering has no request and no session, and the real client would send every page to `/login`

Writes in the demo do nothing. That is the point.

## Seed data

Both seed scripts hold to one standard, written out in [`docs/plan.md`](docs/plan.md): **no screen renders empty.** Every list scrolls, every filter has matches, every enum value has rows, every chart bar has a value, and the month in progress has enough activity that the dashboard does not open on a blank slate.

Both scripts assert that before exiting, and fail loudly if it does not hold. Those assertions earned their place — they caught a status rule that left the current month with no completed orders, a calendar fill that starved one end of its window, and a scheduling pass that piled an extra month of revenue into a single chart bar.
